# 단계별 개발과 별도 검증

## 원칙

기능 단위로 구현하고 최소 검사를 통과한 작업 버전을 GitHub에 올린다.
모든 변경마다 전체 기기·화면 검증을 반복하지 않는다. 상세 검증은 별도 작업으로
진행하고, 발견된 문제는 해당 커밋을 기준으로 수정 커밋을 추가한다.
검증 전 버전을 검증 완료 버전이라고 표시하지 않는다.

## 한 작업 단위

1. 구현 범위와 변경 파일을 정한다.
2. 구현 후 Android 빌드와 변경 기능의 핵심 자동 테스트를 실행한다.
3. 사용자에게 보이는 변경은 영향받는 실제 화면과 흐름을 짧게 확인한다.
4. 통과한 변경과 직접 관련된 테스트를 함께 커밋·푸시한다.
5. `docs/STATUS.md`에 커밋/태그, 통과한 검사, 실패, 별도 검증 항목을 남긴다.

빌드 실패나 변경 때문에 깨진 핵심 테스트를 무시하고 버전 태그를 붙이지 않는다.
기존 실패는 원인과 영향을 구분해서 기록한다. 특히 재화 차감·아이템 지급·
기존 데이터 마이그레이션은 최소 검사에 포함한다.

## 버전 구분

폴더를 v1/v2로 복사하지 않고 Git 커밋과 태그를 사용한다.

| 버전 | 범위 |
|---|---|
| `v0.2.0` | 기존 친구 꾸미기, 액세서리 30종·5부위 장착 저장, 우상단 설정 |
| `v0.3.0` | 데모 재화·임시 가격을 이용하는 로컬 상점 구매 목업 |
| 패치 버전 | 해당 기능의 오류 수정. 예: `v0.3.1` |

상점의 코인과 가격은 확정 경제 규칙이 아니다. 현금 결제, 현금 환전,
실제 활동 보상, 서버 지갑, 전체 사용자 랭킹은 이번 버전에 포함하지 않는다.
데모 재화라는 사실은 앱과 버전 기록에서 구분한다.

## 저장소 운영

- 현재 작업의 기준 커밋과 업로드 브랜치를 확인한 뒤 작업한다.
- 공유 작업 폴더의 다른 변경을 되돌리거나 무차별 `git add .`로 포함하지 않는다.
- 별도 배포 작업 브랜치에 올리고 `main`이나 다른 기능 브랜치를 강제로 덮어쓰지 않는다.
- 태그는 실제 최소 검사를 통과한 커밋에만 붙인다. 이미 공개한 태그를 이동하지 않는다.
- SDK 로컬 경로, Firebase 로컬 구성, 키, 토큰, APK·빌드 출력, 개인 기기 캡처는 제외한다.
- 앱 빌드에 필요한 제작 에셋만 추적하고 콘셉트 이미지·개인 발표 자료는 별도로 관리한다.

## 별도 검증

검증 담당은 버전 태그 또는 커밋을 고정해 재현한다. 담당자를 임의로 지정하지 않는다.
확인 항목은 실제 휴대폰/다른 API, 화면 크기·다크 모드·가로 배치,
권한 허용/거부/철회, 재실행·화면 재생성, 접근성, 장시간 사용이다.
AI 실제 응답 검증은 외부 설정·사용자 동의가 필요한 별도 항목이다.

문제 보고에는 기준 커밋, 재현 절차, 기대/실제 결과, 환경, 필요한 최소 증거를 남긴다.
수정 버전에서 관련 회귀를 확인한 뒤 검증 결과를 갱신한다.
